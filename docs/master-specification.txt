5. AI PIPELINE AND WORKFLOW
Follow the user-provided workflow diagram where consistent with the actual participant guide. Implement these separate stages/modules with simple Python orchestration and structured inputs/outputs:
1. **Pre-safety gate:** validate input length/format, detect likely prompt injection as a supplemental warning, identify sensitive data and mask/redact it where appropriate. Keyword rules alone are not a sufficient security boundary.
2. **Triage Agent (LLM):** classify category, assess priority and explain rationale using the guide; identify evidence/tool needs; return schema-valid JSON.
3. **Retrieval module/agent:** retrieve relevant policy chunks from Pinecone and return real citations and relevance metadata.
4. **Data module/agent:** execute only predefined safe read-only pandas analysis functions over the active validated CSV versions.
5. **Workflow/decision module:** deterministic rules map priority/category/safety and guide-defined approval/escalation conditions to next-step routing, escalation reason, and team/SLA only if supported by source data.
6. **Answer Writer / Evidence & Resolution Agent (LLM):** synthesize only retrieved policy evidence and validated tool outputs into recommended next steps, explaining any uncertainty.
7. **Final safety gate:** validate output schema, verify citations against retrieved sources, check sensitive-data leakage, reject unsupported claims and unsafe instructions, and mask sensitive values again where appropriate.
8. **Response/persistence:** return structured JSON to the UI; save an incident/case and safe audit metadata when the user submits an incident or explicitly chooses to create one.

This preserves a simple orchestrator: the two core LLM roles are Triage Agent and Answer Writer; retrieval, CSV analytics, workflow policy and safety gates can be deterministic tools/modules. Do not pretend each module is an autonomous LLM agent. Document the sequence and fallback behavior.

Mandatory behavioral requirements:
- Follow actual categories, priority meanings and escalations in the participant guide.
- The LLM does not have the authority to override backend permission checks, safety rules, required escalations, or deterministic outputs.
- Explicit safety/security incidents and guide-defined critical cases must follow the required escalation path.
- If the supplied diagram says to escalate when P1, confidence below 0.60, restricted data is requested, or approval is needed, implement those conditions unless the participant guide defines different thresholds/rules; explain any discrepancy. Treat model confidence carefully: if it is not calibrated, call it an estimate rather than a probability.
- Avoid applying a generic P1 rule to everything merely because a service is unavailable. Use guide definitions and incident context.
- When evidence is missing, contradictory, stale or irrelevant, abstain or ask a clarifying question instead of fabricating a policy answer.
- Policy citations must refer to retrieved, existing source text. Never generate filenames/sections from memory.
- Retrieved documents and user text are untrusted content and must never override the system/developer policy or authorize tools/actions.
- Numeric claims must come from deterministic analysis results wherever available.
- Provide safe, useful failure messages if Groq, Pinecone, MongoDB or Python service is unavailable; do not return fake success.
- Keep human approval for consequential actions. The product recommends and records internal cases; it does not conduct real business transactions.
